# v0.2: install in one step, and an MCP server

Part of the Ajiya roadmap. Read `00-build-plan.md` first: it says how this spec
is planned and built. This spec says what v0.2 contains.

## Why

First impressions decide whether people keep a developer tool. Today a new user
has to install a binary, run `init`, and then teach each agent how to use the
CLI. v0.2 makes that one install step, and gives agents structured tools instead
of shell output to parse.

How the pieces fit, which the README must also explain in these terms:

```
once per computer:  install Ajiya, which offers to register it with the agents it finds
once per project:   ajiya init (or the agent runs it when asked)
every day:          open your agent; it starts `ajiya mcp` itself when a session starts
```

Nobody starts the MCP server by hand. Each agent launches `ajiya mcp` in the
background for a session and closes it afterwards. Nothing runs when no agent is
open.

## Part 1: `ajiya status`

A short summary an agent reads at the start of a session. Needed by the MCP
server, and useful on its own.

- Per milestone, in order: done / required, and how many can start now.
- Tickets in progress, with their app and how long since they started.
- How many can start now, and the first three from `next`.
- Tickets marked `Needs a human`.
- Check results: number of errors and warnings.
- The last five activity entries.
- `--json` for all of it; `--brief` for three lines at most.

Done when: golden output for a fixture plan, plain, `--brief` and `--json`.

## Part 2: `ajiya mcp`

An MCP server over stdio, in the same binary, calling the same code as the CLI.
There is no second implementation of any command.

### Library

Use the official Go SDK for MCP if it is mature enough when you start. If it is
not, implement the few messages needed (`initialize`, `tools/list`,
`tools/call`) directly. Either way, **ask me before adding the dependency**, as
the build prompt requires.

### Which project

- The project is the nearest `ajiya.toml` found by walking up from the working
  directory the agent starts the server in. Also accept the MCP `roots` the
  client sends, when it sends them, and a `--dir` flag.
- With no project found, every tool except `ajiya_init` returns a short error:
  "This folder is not set up for Ajiya. Run ajiya init, or call ajiya_init."

### Tools

Each tool returns the same JSON as the matching CLI command with `--json`, plus
a one-line text summary. Tool descriptions are one or two sentences and say when
to use the tool, not just what it does. Keep names stable: they are an API.

| Tool | Mirrors |
|---|---|
| `ajiya_status` | `ajiya status` |
| `ajiya_next` | `ajiya next` |
| `ajiya_ticket_show` | `ajiya ticket show` |
| `ajiya_phase_list` | `ajiya phase list` |
| `ajiya_milestone_list`, `ajiya_milestone_show` | `ajiya milestone list/show` |
| `ajiya_check` | `ajiya check` |
| `ajiya_ticket_add`, `ajiya_ticket_edit` | the same commands |
| `ajiya_ticket_start`, `ajiya_ticket_done`, `ajiya_ticket_block` | the same commands |
| `ajiya_phase_add`, `ajiya_app_add` | the same commands |
| `ajiya_milestone_add`, `ajiya_launch_set` | the same commands |
| `ajiya_init` | `ajiya init --yes` |

**Not offered over MCP**, on purpose, because a person decides these:
`ticket drop`, `app remove`, `milestone remove`, `milestone move`,
`hook install`, and in v0.3 `change approve` and `change reject`. This is the one
place Ajiya can enforce "a person decides" for agents that use MCP. Write this
list into a test, so a new tool cannot be added to MCP by accident.

### Behaviour

- `ajiya_ticket_done` keeps the same rule as the CLI: it refuses without a
  commit that references the ticket. The server never makes commits.
- No network listener. stdio only.
- File access stays inside the project folder. The only programs it runs are
  `git` and the test command from `ajiya.toml` (for `ticket done --test`).
- Errors come back as tool errors with the same one-line message the CLI prints.

Done when: protocol tests run `initialize`, `tools/list` and `tools/call` over
in-memory pipes; a golden file holds the `tools/list` output; a parity test
checks every tool's JSON against the CLI's `--json`; the excluded-tools test
passes.

## Part 3: registering with agents

```
ajiya mcp install [--claude] [--codex] [--cursor] [--all] [--scope user|project] [--yes]
ajiya mcp uninstall [same flags]
ajiya mcp status
```

- For each agent, add one entry that runs `ajiya mcp`. **Check each agent's
  current documentation for the exact config location and format when you
  build this. Do not rely on memory.** As a starting point only: Claude Code has
  a `claude mcp add` command; Codex reads MCP servers from its `config.toml`;
  Cursor reads an `mcp.json`.
- Prefer the agent's own command when one exists. Otherwise edit its config file.
- Before editing a file: show the change, keep a backup next to it, preserve
  every other entry and comment you can, and ask unless `--yes`.
- Running it twice changes nothing the second time.
- `ajiya mcp status` lists each agent found on the machine and whether Ajiya is
  registered with it.
- `ajiya init` runs the same detection and, if Ajiya is not registered with an
  agent it finds, offers to register it.

Done when: tests with a temporary home folder cover each agent's config: first
install, second install (no change), other servers kept, uninstall, and a
malformed existing file (refused with a clear message, nothing written).

## Part 4: install channels

Building on the GoReleaser and Homebrew tickets from v0.1:

- **Install script** at a stable URL: detects the platform, downloads the
  release archive, verifies its checksum against the release's checksum file,
  installs to a user-writable folder, then asks whether to run
  `ajiya mcp install --all`.
- **npm package** `ajiya`, so `npx ajiya init` works: a thin package that fetches
  the matching release binary and verifies its checksum. No JavaScript
  reimplementation.
- Homebrew does not edit user config. After install it prints the one command to
  register with agents.
- The README and the landing page get one install line each and a short
  "what just happened" note using the three-line explanation at the top of this
  spec.

**Publishing anything (script URL, npm, Homebrew tap, plugin) needs my approval
first**, as always.

## Part 5: Claude Code plugin

A plugin in `plugin/` that bundles, for Claude Code users:
- the Ajiya skill
- the MCP server entry (`ajiya mcp`)
- a session-start hook that runs `ajiya status --brief` in projects that have
  `ajiya.toml`, so every session starts with the current state

The plugin cannot ship the binary for each platform. If `ajiya` is missing, the
hook prints the install line and nothing else. Check the current plugin
documentation for the manifest format and how marketplaces work before building.

Also add an "Add to Cursor" link in the README if Cursor's documentation offers
an install link format for MCP servers.

Done when: the plugin validates against Claude Code's plugin checks (or the
documented schema), and a test runs the hook script with and without `ajiya` on
the path.

## v0.2 definition of done (a "Needs a human" sign-off ticket)

On a clean user account, in under ten minutes, following only the README:
1. install Ajiya with the script or Homebrew;
2. register it with Claude Code and with Codex;
3. open each agent in a new empty repository and ask it to plan a small project;
4. the agent sets up the project and plans it through MCP tools, not shell
   commands;
5. it completes one ticket end to end, with a commit and `ajiya_ticket_done`.

Record what happened in the sign-off report, including anything that took longer
than expected.
