# v0.3: decisions, and plan changes that keep history

Part of the Ajiya roadmap. Read `00-build-plan.md` first: it says how this spec
is planned and built.

Work in this repository as usual: follow `.claude/skills/ajiya/SKILL.md`. Plan the
work with `ajiya` commands before writing code, one ticket at a time, commits with
1 to 3 `Ajiya:` references, `go test ./...` and `ajiya check` before you finish.

This is **v0.3**. Put its tickets in a new phase, `decisions-and-changes`. They
come after v0.2: the first of them depends on the v0.2 sign-off ticket. Nothing
in v0.1 or v0.2 depends on them.

v0.2 adds an MCP server. Every new command in this spec also gets its MCP tool,
except `change approve` and `change reject`, which stay person-only and are
listed in the MCP excluded-tools test.

## Why

Plans change. A project decides on PostgreSQL on AWS RDS, completes 60 tickets,
then moves to Supabase. Today an agent would have to reread the whole plan to
find what the move affects, and would probably rewrite tickets, losing the record
of what was done and why.

Ajiya should handle this the way git handles code: never rewrite history, record
the change, and link the old work to the new.

The split of work stays the same as everywhere else in Ajiya:
- **The CLI** finds the tickets a change *might* affect, from structured data.
  This is cheap and deterministic.
- **The agent** judges each candidate: affected or not, and how. It sees only the
  candidates, never the whole plan.
- **A person** approves before the plan changes.

## Part 1: ticket context

A change can only be traced if tickets say what they touch.

### 1a. A Tags column

Phase files gain a seventh column, `Tags`, between `Depends` and `Status`
(Status stays last):

```
| ID | App | Ticket | Done when | Depends | Tags | Status |
| AJ-0107 | api | Configure RDS backups | Daily snapshot, 7-day retention | AJ-0101 | tech:aws-rds comp:database dec:DEC-0003 path:infra/rds/** | 🟩 Done · 4f2a91c |
```

- Tags are space separated `key:value` pairs. Keys: `tech` (a technology or
  service), `comp` (a component), `dec` (a decision ID), `path` (a file glob).
  Values are lower case; `tech` and `comp` values are slugs.
- `ticket add` and `ticket edit` take `--tech`, `--comp`, `--decisions`,
  `--paths` (comma separated). The CLI writes the Tags cell; nobody types it.
- The reader accepts old six-column files and the writer upgrades them. Running
  `ajiya check` on an old file reports it once as a warning, and any write
  command rewrites the file in the new form. The round-trip tests cover both.
- `ajiya tags` lists every tag in use with its ticket count, so agents reuse
  existing values instead of inventing near-duplicates (`postgres` against
  `postgresql`). `check` warns about two `tech` or `comp` values that differ only
  by punctuation or a trailing `ql`, `js` or `s`.

### 1b. Files from commits

`ajiya ticket files <ID>` lists every file changed by commits that reference the
ticket, read from git. This is computed when asked, not stored: git already has
it. Agents never have to guess or maintain a file list.

## Part 2: decisions

A decision records a choice the plan rests on: "Use PostgreSQL on AWS RDS".

- Stored one per file, in `ajiya/decisions/DEC-0003.md`, written only by the CLI:

```markdown
<!-- Written by ajiya. Do not edit by hand: use ajiya commands. -->
# DEC-0003: Use PostgreSQL on AWS RDS

Status: Accepted · 2026-09-12 · decided by Aliyu
Tags: tech:postgres tech:aws-rds comp:database

## Context
<why the choice was needed>

## Decision
<what was chosen>

## Consequences
<what follows from it, including what it rules out>
```

- IDs: `DEC-` and four digits, their own sequence, permanent.
- Status: `Proposed`, `Accepted`, or `Superseded by DEC-xxxx (CHG-xxxx)`.
- Commands: `ajiya decision add "<title>" --decision "<text>" [--context]
  [--consequences] [--tech] [--comp] [--by <name>]`, `decision show <ID>`,
  `decision list [--tag <key:value>]`, `decision accept <ID> --by <name>`. All
  with `--json`.
- `ticket show` lists the decisions a ticket links to, with their status, so an
  agent reads only the decisions that matter for the ticket in hand.
- Checks: error for a ticket linking a decision that does not exist; warning for
  an open ticket linking a superseded decision.

## Part 3: the superseded status

A new closed status for work the plan no longer wants, **keeping what happened**:

```
🟩 Superseded by AJ-0201 · CHG-0014 · was: Done · 4f2a91c
```

- It keeps the original status and evidence after `was:`. Completed work stays
  recorded as completed.
- Superseded and dropped tickets are excluded from progress totals and from
  milestone required sets, so percentages are not inflated by replaced work.
- Tickets that depended on a superseded ticket are moved to depend on its
  replacement when the change is applied (Part 4).
- Set only by applying a change. There is no `ticket supersede` command.

## Part 4: change requests

### 4a. Snapshots

`ajiya snapshot <name>` creates an annotated git tag `ajiya/plan/<name>` on the
current commit, refused if `ajiya/` has uncommitted changes. The plan is in git,
so a snapshot is a tag, not a copy. `ajiya snapshot list` lists them.
`ajiya change open` makes one automatically.

### 4b. Opening a change

```
ajiya change open "Move the database from AWS RDS to Supabase" \
  --replaces tech:aws-rds --with tech:supabase [--decision DEC-0003]
```

- Creates `ajiya/changes/CHG-0014.md` (written only by the CLI), status `Open`,
  and the snapshot `ajiya/plan/before-CHG-0014`.
- `--replaces` takes one or more tags. `--decision` names decisions this change
  would supersede. `--paths` takes file globs the change touches.

### 4c. Finding candidates (deterministic)

`ajiya change impact CHG-0014` lists tickets that *might* be affected, each with
the reasons it was picked:

| Reason | How it is found |
|---|---|
| `tag` | the ticket has one of the replaced tags |
| `decision` | the ticket links a decision the change names |
| `path` | the ticket has a `path` tag, or a commit referencing it changed a file, matching a glob given to `change open --paths` (for example `infra/rds/**`) |
| `downstream` | the ticket depends, directly, on a candidate picked for any reason above |

Only one level of `downstream`. Deeper chains are reached when the agent marks a
ticket `modify` or `replace` and runs `impact` again. The candidates are written
into the change file as a table with an empty verdict column. Running `impact`
again keeps verdicts already given.

### 4d. Judging candidates (the agent)

```
ajiya change assess CHG-0014 AJ-0107 --verdict replace \
  --reason "Uses the RDS backup API directly" \
  [--title "Configure Supabase backups" --done-when "..."]
```

Verdicts, and nothing else:

| Verdict | Means | On approve |
|---|---|---|
| `unaffected` | nothing to do | nothing |
| `modify` | still needed, but its text or tags change | open ticket: edited. Done ticket: a new follow-up ticket is added, depending on it |
| `replace` | needs a new ticket in its place | new ticket added; the old one superseded by it |
| `invalidate` | no longer needed at all | superseded, with no replacement |
| `investigate` | cannot tell yet | blocks approval until changed to another verdict |

`replace` and `modify` of a done ticket need `--title` and `--done-when` for the
new ticket. Every verdict needs `--reason`.

### 4e. Approving

`ajiya change approve CHG-0014 --by <name>` applies every verdict in one write:
new tickets, edits, superseded statuses, dependency moves, decisions superseded
(a new decision given with `--new-decision DEC-xxxx` becomes the replacement).
The change file records who approved it and when, and lists every ticket it
created or superseded.

- Refused while any candidate has no verdict or has `investigate`.
- `ajiya change reject CHG-0014 --by <name> --reason "..."` closes it without
  touching the plan.
- The agent guide must say plainly: agents never run `approve` or `reject`.
  Only a person does, because this is the one command that changes many tickets
  at once. Show the person the impact table and the verdicts first.

`ajiya change list` and `change show <ID>` (with `--json`) complete the set.
`ticket show` lists changes that touched the ticket.

### 4f. Checks

- Error: a change file or decision file that does not round-trip (hand edit).
- Error: a superseded ticket whose replacement does not exist.
- Warning: a change open for more than 14 days.

  and change files, and the upgrade from six columns.
- One scenario test in a temporary git repository that runs the whole Supabase
  example: a plan with RDS-tagged tickets (some done with commits, some open, one
  downstream), a decision, `change open`, `impact`, `assess` with every verdict,
  `approve`, then checks the result: new tickets, superseded tickets with their
  old evidence kept, moved dependencies, the superseded decision, correct totals
  and `ajiya check` passing.

## Do not change without asking me

- Nothing is ever deleted or rewritten: work is superseded, with a link.
- The CLI never calls a model. Candidate finding is deterministic; judgement is
  the agent's; approval is a person's.
- Dependencies stay on tickets, and the commit rule stays as it is.

## Update: keep ticket context light

This update overrides Part 1 and Part 4c where they differ.

- All tags are optional. A ticket with no tags is valid, and `check` must not
  warn about missing tags.
- Drop the `comp` tag. The App column already says which component a ticket
  belongs to. Tag keys are now `tech`, `dec` and `path` (so no `--comp` flag on
  `ticket add`, `ticket edit` or `decision add`).
- Agents add a `tech` tag only when a ticket depends on a specific technology or
  service: `tech:aws-rds` on "Configure RDS backups", but no tag on "Add a
  booking form". The agent guide states this rule.
- `path` tags are for tickets whose files can't be learned from commits yet,
  such as open tickets. Once a ticket has commits, `ajiya ticket files` reads
  them from git.
- Never store what the CLI can work out: files, commits, readiness, milestone
  membership.
- A new ticket field is added only if a command uses it.
- `change impact` must still work on tickets with no tags. It finds them through
  dependencies, decisions and the files in their commits.
