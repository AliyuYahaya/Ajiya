## Why

In the legacy format (MedInformer), the rollout WBS groups tickets from several
area files (API, CMS, frontend) into RO work packages. Each package delivers one
feature, and packages sit under ordered headings: "Gate 0: Staging proven",
"Phase A: Safety", through "Phase F: After launch".

An Ajiya phase is meant to be exactly that feature grouping. But `import legacy`
does the opposite today: each area file becomes a phase, and each RO package
becomes a single ticket in a `rollout` phase. After an import, RO-021 "Production
host and deploy" is one checkpoint ticket, and its real tickets are spread across
area phases. The feature grouping is lost.

Ajiya also has only one launch target, so the ordered gates are lost too.

This task fixes both, and adds a display order for phases. Do Part A first,
because Part B uses it.

## Part A: milestones

A milestone is a named gate. The project can have several, in order. Each one
works out its required tickets the same way `launch` does now.

### A1. Config and model

```toml
[[milestones]]
name = "staging-proven"
targets = ["gate-0"]                 # phase slugs or ticket IDs

[[milestones]]
name = "launch"
targets = ["go-live"]

[[milestones]]
name = "after-launch"
targets = ["reporting", "AJ-0142"]
```

- Order is the order in the file.
- `name` is a slug, unique. `targets` is a non-empty list of phase slugs or
  ticket IDs.
- Required set of a milestone: every ticket of its targets (all of a phase's
  tickets, or the ticket itself) plus everything they depend on, directly or not.
  This is `plan.Required`, extended to a list of targets.
- A ticket belongs to the **earliest** milestone whose required set contains it.
  A ticket in no required set is **unscheduled**.
- The old `[launch] target = "x"` keeps working and means one milestone named
  `launch` with target `x`. A file with both `[launch]` and `[[milestones]]` is a
  config error that says to move the launch target into the list.

Done when: table tests cover several milestones, a ticket required by two
milestones (belongs to the earlier), unscheduled tickets, and the old `[launch]`
form.

### A2. Commands

| Command | Does |
|---|---|
| `ajiya milestone add <name> --targets <list> [--before <name> \| --after <name>]` | Adds one; default is last |
| `ajiya milestone list` | Each milestone in order: done / required, and how many can start now |
| `ajiya milestone show <name>` | Required tickets not done, what blocks them, and what needs a human |
| `ajiya milestone move <name> --before <name> \| --after <name>` | Reorders |
| `ajiya milestone remove <name>` | Removes it; tickets are not touched |

- `launch set` and `launch show` become shorthand for the milestone named
  `launch`. Existing tests for them must still pass.
- All of these accept `--json`.
- `ajiya next` sorts by earliest milestone first, then by how many tickets each
  one unblocks, and shows the milestone name. Its JSON gains a `milestone` field
  (empty for unscheduled).

Done when: CLI tests in a temporary repository cover each command, the JSON
output and the new `next` order.

### A3. Checks

- Error: a target that is neither a phase nor a ticket; a duplicate name.
- Warning: an earlier milestone's required set contains every ticket of a later
  milestone's targets, so the later gate is reached no later than the earlier
  one. Their order is probably wrong.
- Warning: open tickets that are unscheduled, when milestones exist. List up to
  10 IDs.

Each with a stable code, as the other checks have.

### A5. Phase display order

People want to read phases in a sensible sequence. Add an order that is **for
display only**: it never changes what can start, what `next` returns or what a
milestone requires. Ticket dependencies stay the only source of what comes first.

- Stored in `ajiya.toml`:

  ```toml
  [phases]
  order = ["accounts", "bookings", "admin", "go-live"]
  ```

  Phases missing from the list come after it, in suggested order (below). A slug
  in the list that is not a phase is an error.
- `ajiya phase move <slug> (--before <slug> | --after <slug> | --first | --last)`
  changes the list. `phase rename` updates it.
- `ajiya phase list` shows phases in display order, each with done / total and
  its earliest milestone. `--json` too.
- `ajiya phase order --suggest` prints an order worked out from the dependencies;
  `--apply` writes it to the list. How it is worked out:
  - Phase A comes before phase B when a ticket in B depends on a ticket in A.
  - Sort phases so each comes after the phases it waits on (a topological sort).
  - Ties: earliest milestone first, then the order the phases were created.
  - Phases that wait on each other (features often interleave) are kept next to
    each other in creation order and reported as info, not as an error.
- `check` warning: a phase listed before another phase that it waits on, when
  the two do not wait on each other. Name both phases and one ticket link that
  shows it.
- Everything that lists phases uses the display order: `PROGRESS.md`, the
  dashboard data, `phase list`, `next --json` grouping, and the files `init`
  writes.
- `import legacy` sets the display order from the order of packages in the
  rollout file.

Done when: table tests cover the suggested order with ties, a phase cycle and a
milestone tie-break; CLI tests cover `phase move`, `phase list` and
`phase order --suggest --apply`; the check warning has a fixture.

## Part B: `import legacy` maps each RO package to a phase

Change the mapping in `internal/cli/cmd_import_legacy.go` and its package
comment. The parsing rules in `internal/importer/legacy.go` stay as they are.

### Mapping

1. **Each RO package becomes a phase.**
   - Slug: the RO number and the first words of its name, for example
     `ro-021-production-host-and-deploy`, at most 40 characters, unique.
   - Title: the RO name as written. Goal: the RO name, ending `(was RO-021)`.
   - The tickets its scope counts move into this phase.
2. **Tickets keep their area as their app.** Add an optional `app` key per source
   in the legacy config. A source without one uses `--app` (default `infra`), as
   today. The app must be registered; refuse with a clear message if it is not.
3. **A package with no scope** (for example user acceptance, or cutover) becomes a
   phase with one ticket: title = the RO name, status from its typed status. If
   it is pending, mark it `Needs a human: rollout task carried from RO-xxx; check
   who does it`.
4. **Dependencies between packages.** When package A depends on package B, each
   *root* ticket of A (no dependency inside A) depends on each *sink* ticket of B
   (nothing inside B depends on it). Every ticket in A then waits for all of B,
   through the chain, with fewer links than a full cross product. Links that would
   make a loop are left out and reported, as today.
5. **A ticket in more than one package** goes into the first in file order. The
   report lists it with the other packages that named it.
6. **Cross-references** (a ticket "tracked as" another ticket in the same
   package) are imported as `🟩 Dropped: tracked as <new ID> (was <old ID>)`,
   decided by `ajiya import`, so the work counts once. The report lists them so a
   person can reopen any of them.
7. **Open tickets in no package** go to a phase `inbox`. **Done tickets in no
   package** go to a phase `archive` with the goal "Done before Ajiya, not in any
   rollout work package".
8. **Headings become milestones.** Each `##` heading in the rollout WBS becomes a
   milestone, in file order: `name` from the heading (for example `gate-0`,
   `phase-a`), `targets` = the phases made from the packages under it. Skip a
   heading with no packages.
9. **Without a rollout WBS**, keep today's behaviour: one phase per area file.

Old ticket IDs stay as aliases, as today. There is no RO ticket any more, so
`ajiya ticket show RO-021` no longer finds anything. The import report maps each
RO ID to its phase slug, and `--json` prints the same mapping.
